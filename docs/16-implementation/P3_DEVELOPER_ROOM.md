# P3 developer combat room

Status: ACTIVE — PHYSICAL GATE HARNESS

P3 has an entity-backed in-world integration harness.

It is deliberately called a "room" even though the current implementation is a lightweight lane around the developer's current position. Building permanent map geometry here would confuse integration testing with world production.

## Commands

```text
/worldrpg p3 room spawn
/worldrpg p3 room spawn <distance>
/worldrpg p3 room move <distance>
/worldrpg p3 room health <0-100>
/worldrpg p3 room cast focus
/worldrpg p3 room cast bolt
/worldrpg p3 room cast channel
/worldrpg p3 room status
/worldrpg p3 room reset
```

Default spawn distance is 3 blocks.

Spawn/move distance accepts 1–30 blocks.

## Target

The harness spawns a real HuskEntity:

- AI disabled;
- persistent while the harness owns it;
- Minecraft damage invulnerable;
- visible custom name: `P3 RPG Target`.

Minecraft invulnerability is intentional.

P3 fixture abilities mutate the target's RPG HEALTH resource rather than vanilla health. Normal swords/arrows must not contaminate this proof.

The target is discarded on harness reset/replacement and on server shutdown.

## State-preserving move

`/worldrpg p3 room move <distance>` relocates the existing target relative to the player's current position/facing.

It deliberately preserves:

- entity UUID;
- CombatActor binding;
- RPG resources;
- current cast target identity.

This command exists so a cast can begin legally and then fail fresh range validation at resolution without confusing the test with source movement interruption.

For the range-revalidation row:

1. spawn at 3 blocks;
2. begin Bolt;
3. keep the player still;
4. run `/worldrpg p3 room move 20` before Bolt resolves;
5. verify the cast is rejected/interrupted at resolution and target RPG health did not change.

## Proof-health setup

`/worldrpg p3 room health <0-100>` changes only the target's RPG proof-health.

It does **not** change the Husk's vanilla Minecraft health.

This exists because the proof player starts with 100 mana and the authored proof ability costs/damage cannot naturally reduce a fresh 100-health target to zero before mana exhaustion.

That mismatch is acceptable for mechanism fixtures; it must not make the RPG-exhaustion gate impossible to test.

For the exhaustion row:

```text
/worldrpg p3 room health 0
```

then request Bolt/Channel and verify the server rejects because the target's RPG health condition fails while the invulnerable Husk remains physically present.

## Direct room activation

`/worldrpg p3 room cast <ability>` calls the same server P3 combat runtime using the room-owned target, but deliberately bypasses the C2S packet/replay layer.

It exists for server-condition rows the temporary vanilla crosshair cannot submit:

- target behind a solid LOS blocker;
- target beyond vanilla crosshair reach.

The command prints `(network path bypassed)` in its feedback so it cannot be confused with network evidence.

### Important evidence rule

Direct room activation **does not prove networking**.

The client-intent/network row still requires the F7/F8 path:

```text
client key
-> C2S payload
-> server replay guard
-> P3 runtime
-> S2C response
```

Use direct room activation only where the temporary crosshair itself prevents constructing the server validation case.

## Why the Bolt proof cast is long

The authored proof Bolt uses an intentionally exaggerated developer duration so a human tester has time to:

- run `room move`;
- place a LOS blocker;
- inspect status while the cast is committed.

That duration is not combat balance.

Proof fixture timing exists to make mechanism evidence observable.

## Channel observability

The proof Channel produces three scheduled one-second ticks.

During the channel, the developer runtime echoes each `ResourceChangedEvent` generated by the cast to the source player.

Expected target proof-health sequence from a fresh 100-health target:

```text
100 -> 95
95 -> 90
90 -> 85
```

followed by the cast-completed message.

This lets the physical test prove three scheduled resolutions rather than merely observing one final `-15` result.

## Why distance is configurable

Fixture abilities demonstrate different range limits.

The room can intentionally create:

- a clearly valid close-range target;
- a target near the limit;
- a target outside the limit.

This lets us falsify range behavior rather than only confirming the happy path.

## Current manual proof flow

The authoritative row-by-row procedure lives in:

`docs/16-implementation/P3_PHYSICAL_EVIDENCE_RUNBOOK.md`

The short version is:

1. reset/spawn a fresh close target;
2. record actor/resource baseline;
3. prove real F7 C2S activation;
4. prove committed timed cast and persistent mana;
5. prove movement interruption;
6. prove fresh range revalidation using state-preserving target move;
7. prove LOS rejection and LOS revalidation;
8. prove explicit out-of-range rejection;
9. prove three channel ticks and channel interruption;
10. prove item + aura share the stat engine;
11. prove RPG exhaustion independently of vanilla Husk health;
12. prove server cooldown/GCD authority;
13. prove cleanup and physical observation;
14. preserve CI/headless parity.

## What this proves

Once manually exercised, this harness tests the complete path:

```text
physical Minecraft world
-> real living source/target
-> client developer input
-> Fabric C2S payload
-> replay guard
-> server entity resolution
-> server target observations
-> RPG conditions/resources/cooldowns
-> server cast lifecycle
-> generic effects
-> RPG actor state
-> structured S2C response
```
